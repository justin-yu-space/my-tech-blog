加了 rerank 后 MRR 从 0.51 涨到 0.78，延迟也涨到 620ms：这买卖怎么算

file-manager 的搜索框一直有个说不清的毛病：用户输入「2026 预算 汇总」，正确的那份 Excel 明明在库里，但排在第七条。点开前三条都是名字沾边的旧文件。召回阶段它确实被找出来了——问题不在「找没找到」，而在「排得对不对」。这就是 rerank 该上场的地方，也是我第一次真切感受到「召回」和「排序」是两个完全不同的活儿。

先确认病灶：召回没问题，排序有问题

我用 40 题的评测集量了一遍：recall@50 是 96%，意思是 50 条候选里几乎总有正确文件；但 recall@5 只有 62%，MRR 0.51。三个数字摆在一起，结论很清楚——向量检索把相关文档捞上来了，只是没把它放到前面。原因是 embedding 把整段文本压成一个向量，长文档里真正关键的那句「2026 年度预算汇总表」被稀释了，而文件名里带「预算」两个字的旧文件反而更像。

接一层重排：召回 50，重排 12

做法很标准：向量召回 50 条，把这 50 条原文（不是向量）连同 query 一起送进 reranker，让它逐条打分，取前 12 条交给下游。reranker 是 cross-encoder，query 和文档拼在一起进模型，能看到「预算」和「汇总」在文档里到底出现在哪个位置、什么上下文——这是双塔 embedding 结构上做不到的。

import requests

def rerank(query, docs, top_n=12):
    resp = requests.post(
        "https://api.example.com/v1/rerank",
        headers={"Authorization": "Bearer " + API_KEY},
        json={
            "model": "bge-reranker-v2-m3",
            "query": query,
            "documents": [d["text"] for d in docs],
            "top_n": top_n,
        },
        timeout=1.5,          # 必须设，见下面的坑
    )
    resp.raise_for_status()
    data = resp.json()["results"]      # [{index, relevance_score}, ...]
    return [(docs[r["index"]], r["relevance_score"]) for r in data]

数字：排序变好了，延迟也变贵了

同一套 40 题跑下来：recall@5 从 62% 升到 79%，MRR 从 0.51 升到 0.78，最直观的用户感受是「第一条就对」的比例从一半出头涨到接近八成。代价是延迟：只走向量检索时 P95 是 180ms，加上 rerank 变成 620ms，翻了 3.4 倍。50 条候选送进 cross-encoder，计算量是按「条数 × 长度」线性涨的，这一步没有便宜的办法。

坑一：我想省掉召回，让 reranker 直接干活

第一个念头很自然：既然 reranker 排得准，那干脆别向量召回了，把库里文件全丢给它排。试了一次就被打回——文档上千条，一次请求直接超时，而且 reranker 的分数只在「给定这批候选」内部有相对意义，它不做召回，只做排序。更阴险的是第二个错误：我为了省延迟，只把向量召回的 top5 送进 rerank。结果 MRR 反而掉到 0.49——因为候选池太小，正确文件本来排第 7，压根没进 rerank 的输入。rerank 只能在召回给的池子里挑，池子不够大，它连翻身的机会都没有。我的经验值是：召回 40~60 条，重排取 10~15 条。

坑二：512 token 截断，把关键段落切掉了

上线后有一类文档始终排不准——都是超过 3000 字的长文档。查了半天发现 reranker 的输入上限是 512 token，超了直接截断，被截掉的正好是后半段的正文。我的修法是「按段落切块送排」：一篇长文档拆成 3 个块分别打分，取最高分作为该文档的分数，同时把命中块的位置记下来，便于前端高亮。这一改，长文档那 9 道题的 MRR 从 0.41 提到 0.72。

坑三：超时没设，一个慢请求拖死整个搜索

rerank 是外部调用，我第一版忘了设 timeout。某次网关抖动，单次请求卡了 8 秒，用户的搜索框就一直转圈。重排必须当成「可能失败的可选增强」，而不是主链路。现在的策略是 1.5 秒超时，超时或报错就直接用向量检索的原始顺序返回，页面上不做任何提示——用户拿到的是「稍差一点但很快」的结果，而不是一个错误页。实测这条降级路径的触发率约 0.7%，但它是搜索框可用性的保险。

结论

这笔买卖到底值不值，取决于你的场景能不能吃掉 400ms。内部文件管理这种「一次搜索看十秒」的场景，我认为值：MRR 从 0.51 到 0.78 带来的效率提升，远大于多等半秒的烦躁。但如果是对接 C 端搜索框、要求 200ms 内出结果，我会改用更小的 reranker 或者只对前 20 条重排。rerank 不是「更准的检索」，它是用延迟换排序质量的一道明码标价的交易，先想清楚你的延迟预算，再决定买多少。
