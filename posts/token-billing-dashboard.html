一个月 1200 块的 AI 账单我全靠猜：装了 token 计费看板，当月降了 38%

2026年11月23日·约 9 分钟#AI#成本核算#学习笔记

工作日报系统上线三个月后，老板问我一个问题：「这个月 AI 花了 1200 块，哪个功能烧的？」我答不上来。我只知道调用了大模型 API，账单从最初的 80 块涨到 1200 块，但拆不开——是按部门分的？是摘要功能还是问答功能？有没有哪次死循环把 token 烧光了？那次之后我给系统装了一套 token 计费看板，第一次把「花了多少钱」变成按功能、按部门、按用户可查的数字，当月账单降了 38%。

先纠正一个错误：token 不是「字数除以四」

我最早的成本估算函数是 len(text)/4，这在英文上大致成立，在中文上错得离谱。我用 tiktoken 对比了 500 条真实工艺卡文本：cl100k_base 编码下，一个中文字符平均约 1.5 个 token，有些生僻的零件号甚至一个字三个 token。按除以四估算，我把实际用量低估了 60%——难怪账单总是比我算的高。后来我改成用官方 tokenizer 在发送前精确计数：

import tiktoken

enc = tiktoken.get_encoding("cl100k_base")

def count_tokens(text: str) -> int:
    return len(enc.encode(text, disallowed_special=()))

# 输出 token 单价通常是输入的 3~4 倍，必须分开记
PRICE_IN  = 0.0008   # 元 / 千 token（示例档位）
PRICE_OUT = 0.002

def cost(prompt: str, completion: str) -> float:
    tin = count_tokens(prompt)
    tout = count_tokens(completion)
    return tin / 1000 * PRICE_IN + tout / 1000 * PRICE_OUT

输入和输出不等价，别只看总 token

第二个认知纠正是输入输出价格不对称。我们的摘要功能一次输入 3000 token 工艺卡、输出 300 token 摘要，看起来输出只占 9%，但输出单价是输入的 2.5 倍，实际成本占比接近 43%。早期我按总 token 均摊成本，得出的结论是「摘要很便宜」，完全误导了优化方向——真正该压的是输出端的啰嗦提示，而不是输入端的检索长度。

把成本打到业务维度上

精确计数只是基础，关键是给每次调用打上业务标签。我在调用入口统一封装，强制传 dept、feature、user_id 三个字段，随 trace 一起写入 SQLite 的 token_log 表。这样月底那句「哪个功能烧的」就变成一条 group by 查询。看板出来后发现：60% 的成本来自一个我早忘了的「全库问答」实验功能，它每次把 20 个文件全塞进上下文。砍掉之后当月账单直接降了 38%。

踩过的坑

坑一：流式输出的 token 数拿不到。SDK 流式模式下 usage 字段只在最后一个 chunk 里返回，我一开始每个 chunk 都去读 usage，前面全是 null，把计数全记成了 0。正确做法是累积 chunk 到最后一块，从 final chunk 里取 usage。坑二：缓存命中重复计费。语义缓存命中时根本没调模型，但我的日志在调用前就记了账，导致缓存命中也被算钱。改成「只在真实收到 API 响应后记账」才对。坑三：失败的重试请求也要算钱——有些错误是模型已经生成了一半才断连，token 照烧，不能因为请求失败就不记。

结论

这套看板给我的最大收获不是省钱，而是建立起「AI 调用是有单位成本的工程资源」这个直觉。token 计数要用官方 tokenizer，输入输出分开计价，成本必须能归因到业务维度——做不到这三点，你就是在用信仰管钱。现在每次新功能上线，我都会先看它的单次调用成本，再决定要不要上。省下来的 38% 是结果，真正值钱的是「我知道钱去哪了」。
