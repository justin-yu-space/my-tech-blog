主模型半夜返回 429，我的 AI 摘要全线崩了：加了模型路由 + 退避后可用性到 99.7%

2026年11月23日·约 10 分钟#AI#多模型路由#实践

有天凌晨两点，NPI 系统的工艺卡摘要全线报 429 Too Many Requests。我们只接了一家模型厂商，它那边一限流，整个摘要功能就瘫了，而工艺员第二天一早要量产评审。那次事故之后我做了两件事：按任务难度分级路由到不同模型，以及给调用加上主备切换和指数退避。改完跑了三个月，可用性从大概 98% 提到 99.7%，也踩了一串坑。

不是所有任务都配用大模型

我先统计了两个月的调用：60% 的请求其实是简单任务——判断一封邮件是否紧急、给文件打标签、抽取一个零件号。这些用一个小模型就能做，速度和成本都只有大模型的零头。于是我把请求分三级：light（分类/抽取）走便宜小模型，standard（摘要/问答）走主力模型，heavy（复杂推理）才上最强模型。分级之后整体成本降了一半，简单任务的延迟从 800ms 降到 200ms。

import time, random

def call_with_fallback(task, tier):
    candidates = ROUTE[tier]          # 按优先级排列的模型列表
    last_err = None
    for i, model in enumerate(candidates):
        try:
            return client.chat(model=model, **task)
        except RateLimitError as e:
            last_err = e
            if i == len(candidates) - 1:
                break
            # 指数退避 + jitter，避免惊群
            time.sleep(min(2 ** i, 8) + random.uniform(0, 0.5))
    raise last_err

坑一：没有 jitter 的退避造成惊群

第一版退避是纯 2 ** i，没加随机抖动。结果整点时所有实例同时被限流、同时睡 1 秒、同时重试，又同时被打回来——我们自己做了一个「分布式同步攻击」。加上 random.uniform(0, 0.5) 的 jitter 之后，重试请求被打散，恢复速度快了好几倍。这是分布式系统里很经典的坑，我第一次在自己代码里亲眼见到。

坑二：降级了却不告诉用户

主模型挂了自动切到备用模型，看起来很美好，但备用模型能力弱一档，输出质量悄悄下降。有次用户拿着摘要去做评审，事后发现备用模型漏了关键参数。现在的做法是：每次响应都带上实际使用的 model 和 degraded 标志，前端在降级时用一个小角标提示「当前为备用模型」，让用户自己判断要不要信。降级不是把问题藏起来，是把选择权交还给用户。

坑三：把 400 当成 429 去重试

有次参数写错，模型一直返回 400，我的代码把它归类为可重试错误，退避重试了四次，次次都返回 400——白烧了四次请求的钱和时间。后来我把错误分成三类：429/503 这类瞬时错误才重试，400/401 这类客户端错误直接抛，5xx 里的服务端错误有限重试。重试策略必须按错误码分类，一刀切只会放大问题。

结论

多模型路由的本质是承认「单一依赖必然失败」。分级路由省钱降延迟，主备切换扛住单点故障，而退避、jitter、错误分类这些细节才决定它在真实故障里到底靠不靠谱。三个月稳定运行后我最大的体会是：容灾代码平时看不出价值，但它值的就是那一次凌晨两点的 429。现在每次设计 AI 调用，我都会先问一句「这家挂了怎么办」。
