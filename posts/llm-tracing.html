给每一次 AI 调用装上行车记录仪：我用 trace ID 揪出了烧 token 的元凶

工作日报系统的用户跟我抱怨：「自动周报有时候要等十几秒，有时候一秒就出来，是不是看心情？」我翻了半天应用日志，只看到几行零散的耗时记录，根本拼不出一次请求里到底发生了什么——检索、三次模型调用、两次重试、一次超时回退，全搅在一起。没有全链路追踪，性能问题就只能靠猜。于是我给每次请求装了个「行车记录仪」。

为什么普通日志不够用

一次 AI 请求不是一次调用，而是一串：检索候选、构造 prompt、模型生成、解析校验、失败重试……传统日志按时间平铺，没有统一 ID 把它们串起来。我试过在每条日志里打印用户 ID，但同一用户并发发来好几个请求，日志依旧是一团乱麻。我需要的是一棵 span 树：每个环节是一个 span，共享同一个 trace_id，记录起止时间、耗时、token、输入输出摘要。

用 trace_id 串起整条链

我在请求入口生成一个 trace_id，透传到每个环节。用的是最朴素的实现——一个 async 包裹函数，把每步操作包成 span，成功失败都记录，finally 里算耗时。没引入 OpenTelemetry 那么重的东西，几十行就够我用。

async function traced(name, fn, ctx) {
  const span = { trace_id: ctx.traceId, name,
                 start: Date.now(), attrs: {} };
  try {
    const out = await fn(span);
    span.status = "ok";
    return out;
  } catch (e) {
    span.status = "error";
    span.attrs.error = String(e).slice(0, 200);
    throw e;
  } finally {
    span.ms = Date.now() - span.start;
    ctx.spans.push(span);
  }
}
const answer = await traced("retrieve", () => retrieve(q), ctx);
const draft  = await traced("llm.call", () => llm(q, answer), ctx);

揪出元凶：40% 的 token 花在重试上

追踪跑了一周，把 span 按累计 token 一排序，元凶立刻现形：一次典型的周报生成，主调用只占 60% 的 token，剩下 40% 全在低效重试上——结构化校验失败后，我把整个 prompt（含全部检索上下文）原样重发，一次重试就多烧 3000+ token，而重试率高达 38%，因为校验逻辑对「模型把日期写成字符串」这类小错也直接判失败。

定位到就好办：重试时只发校验失败字段的修正指令，不重发完整上下文；校验规则放宽，类型小错先做规范化而不是判失败。改完同样一份周报，平均 token 从 8200 降到 5100，p95 耗时从 4.1 秒降到 2.6 秒。没有追踪，我根本不知道钱烧在了哪一步。

踩坑：追踪本身的成本与隐私

两个坑。一是追踪不能太贵：一开始我 100% 采样、每个 span 都存完整 prompt 和输出，结果存储涨得比业务数据还快，写追踪本身还引入约 30ms 延迟。改成 10% 采样、出错请求强制保留，span 里只存输入输出的哈希和前 200 字摘要，开销降到 3ms 以内。二是隐私：prompt 里常有员工真实姓名和日报正文，明文落盘是隐患——所有 span 写入前都过一遍脱敏正则，这个不能省。

结论

现在每次慢请求我都能点开一条 trace，逐段看时间花在哪、token 烧在哪一步、重试了几次。可观测性不是出事后的救火工具，而是把「我以为」变成「数据说」的习惯。对 AI 应用尤其重要——模型的不确定性太多，不观测就等于闭眼开车。下一步想把 trace 接到成本看板上，按功能维度统计 token 花费，那是后话。
