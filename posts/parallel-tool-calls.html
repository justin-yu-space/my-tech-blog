让模型一次调 4 个工具：我把周报生成从 11 秒压到 3 秒，也踩了并发的坑

2026年11月20日·约 9 分钟#AI#Agent#实践

工作日报系统有个功能：点「生成周报」，助手要依次查四个数据源——日报库、项目进度、考勤、待办清单，然后汇总成一份周报。四个查询串行跑，每个 2~3 秒，用户要盯着转圈圈等 11 秒。我盯着那段 for 循环想：这四个查询互相没有依赖，为什么要一个等一个？改成并发之后确实压到了 3 秒，但并发带来的坑，比串行慢更让人头疼。

从串行到并发：让模型一次返回多个工具调用

关键一步是让模型在一次回复里返回多个 tool_call。以前我一次只让它调一个工具，拿结果再问下一轮，天然串行。现在我在工具定义里加上「如果需要多项数据，请一次性调用所有相关工具」，模型就会在一个 assistant 消息里给出 4 个 function call，每个带自己的 arguments。

resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=messages,
    tools=TOOLS,
    tool_choice="auto"     # 关键：允许一次返回多个
)
calls = resp.choices[0].message.tool_calls
print(len(calls))          # 常见是 3~4 个
# 每个 call: {id, function: {name, arguments}}

并发执行：线程池 + 信号量限流

拿到 4 个调用后，我用线程池并发执行，同时用信号量把并发数压到 3——因为下游 file-manager 的查询接口有连接数限制，放开了打会直接被拒。这里踩了第一个坑：我一开始把并发设成 4（和工具数一样），下游接口返回了一串 429 Too Many Requests，而模型侧完全正常——限流发生在我自己的业务接口，不在大模型网关。

from concurrent.futures import ThreadPoolExecutor, as_completed
import threading

sem = threading.Semaphore(3)          # 下游接口最大并发

def run_call(call):
    with sem:
        return call.id, safe_execute(call)

results = {}
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(run_call, c) for c in calls]
    for f in as_completed(futures):
        cid, val = f.result()
        results[cid] = val             # 按 id 收集，不依赖完成顺序

坑二：共享上下文的竞态

我的第一版把一个共享的 context 字典传给所有线程，每个工具往里塞结果。四个线程同时写，出现了丢键和脏数据——周报里偶尔少一块内容，重跑又正常。这种 bug 最恶心，因为它偶发。并发执行的第一原则：不要共享可变状态。改成每个工具返回自己的结果、主线程按 call id 汇总后，这类问题彻底消失。

坑三：一个工具失败，整份周报全废

并发之后失败处理也变了。串行时某个查询失败，我直接中断重来；并发时四个已经在飞，一个失败不能拖垮其他三个。我改成「部分成功」策略：每个工具内部自带重试和降级——重试 2 次仍失败就返回一个带 degraded: true 标记的占位数据，同时在周报末尾列出「哪些数据源没查到」。这样用户拿到的是一份标注清楚的周报，而不是一个空白页。代价是要处理「部分数据」的展示逻辑，多写了几十行，但比全盘失败友好得多。

数字与结论

最终效果：四个查询串行 11.2 秒，并发后 3.1 秒（受限于下游接口的 3 并发上限，否则能到 2.8 秒），提速约 3.6 倍。工具调用本身的模型开销几乎没变——省的全是等待时间。并发工具调用提速的本质，是把「等待 I/O」从串行变成重叠，而不是让模型变聪明。但它把复杂度转移到了工程侧：限流、竞态、部分失败，一个都不能少。我现在的原则是：无依赖的查询才并发，并发数看下游最薄弱的环节，共享状态一律不碰，失败按部分成功兜底。
