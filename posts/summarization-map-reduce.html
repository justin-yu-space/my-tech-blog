180 份日报汇总成一页月报：refine 跑了 9 分钟，层级 map-reduce 只要 63 秒

2026年11月24日·约 9 分钟#AI#摘要策略#学习笔记

工作日报系统有个「月度总结」功能：把一个部门一个月的所有日报汇总成一份。上线后我一直不满意——周报还行，一到月度就变成一堆正确的废话，「本月各项工作有序推进」这种句子能出现七八次。我把 180 份日报（约 11.2 万字）丢给模型让它「总结成月度报告」，结果关键的那次量产异常被压得只剩一句「部分环节存在问题」。这不是模型不行，是我用错了摘要策略。我花了两天把三种长文摘要方案各跑了一遍，最后落到一个层级方案上。

三种策略，我一开始只会一种

我最早只会最笨的一种：把全部文本塞进一次调用。11.2 万字中文约合 16 万 token，别说 32k 窗口，就算分段喂进去，模型也会在长上下文里「迷失中间」——开头和结尾记得清楚，中间那批日报几乎不进输出。查资料后我才知道，长文摘要有三条成熟路线：map-reduce（先分块各自总结，再汇总）、refine（逐块滚动改写，每次带上之前的摘要）、hierarchical（分层归约，逐层压缩）。名字看着简单，真跑起来差别巨大。

map-reduce：快是真的快，丢也是真的丢

map-reduce 的思路是每个 chunk 独立总结，再把所有小摘要拼起来做一次 reduce。我把 180 份日报按人按周切成 180 个块，并发 8 路调用（再高就触发 429），每块压成 120 字，耗时约 48 秒。但 reduce 那一步出了问题：180 条摘要拼起来约 2.16 万字，一次塞给 8k 上下文的小模型直接报 context length exceeded；换成 32k 模型后虽然不报错，输出却严重「平均化」——那次持续三天的量产异常（原本在 11 份日报里反复提到）只换来一句「生产略有波动」。

def map_reduce(docs, llm, map_prompt, reduce_prompt):
    # 1) map：每块独立压缩，并发受下游限流约束
    from concurrent.futures import ThreadPoolExecutor
    with ThreadPoolExecutor(max_workers=8) as pool:
        summaries = list(pool.map(
            lambda d: llm(map_prompt + d, max_tokens=300), docs))

    # 2) reduce：小摘要太多时，分批再归约，别一次塞满
    while sum(len(s) for s in summaries) > 12000:
        summaries = [llm(reduce_prompt + "\n".join(batch))
                     for batch in chunks(summaries, 12)]
    return llm(reduce_prompt + "\n".join(summaries))

「分批再归约」这个 while 循环是我第二天才加的。第一版直接一次 reduce，才有了上面那个 429 和平均化。

refine：质量好一点，但 9 分钟谁受得了

refine 是拿上一轮的摘要当上下文，和下一个 chunk 一起再改一版。好处是后面的块能「记得」前面的结论，不会像 map-reduce 那样各说各话。代价是彻底串行：180 步一步不能少，而且每步的输入是「累计摘要 + 新块」，摘要越滚越长。我实测单步耗时从第一步的 1.4 秒涨到最后一步的 6.8 秒，整轮跑了 9 分 12 秒，token 消耗 4.7 万，是 map-reduce 的 2.6 倍。对用户来说，点一下「生成」等九分钟，等于这个功能不存在。

折中方案：先按周归约，再汇总成月

最后我用了层级结构，本质是带业务语义的 map-reduce：先按周把 45 份日报归约成 4 份周摘要，再把 4 份周摘要合并成月度报告。关键在于归约的分组要顺着业务结构切，不能随机分块——同一周的日报本来就在讲同一批项目，放一起归约时模型看到的是连续叙事，跨周的重要事件（比如那次量产异常）反而会在第二次归约时因为被多周提及而自动凸显。

def hierarchical_monthly(daily_reports, llm):
    by_week = group_by_iso_week(daily_reports)   # 4 周，每周 ~45 份
    weekly = []
    for week, reports in by_week.items():
        weekly.append({
            "week": week,
            "digest": reduce_with_focus(llm, reports,
                      focus="只保留：项目进展、异常事件、待决策事项")
        })
    # 第二层：4 份周摘要 -> 1 份月报，保留周次标记
    return llm(MONTHLY_PROMPT + "\n".join(
        w["week"] + ": " + w["digest"] for w in weekly))

其中 reduce_with_focus 的 focus 提示是另一个收获：与其让模型「总结全部」，不如明确告诉它只留哪三类信息。加上这句后，「有序推进」这类套话基本消失，异常事件的保留率从 3/8 提到 8/8（我用 8 个已知关键事件做的核对表）。总耗时 63 秒，比 refine 快了近 9 倍，token 降到 2.1 万。

踩过的坑

坑一：表格被切碎。日报里有工时表格，按字符数切块会把行列拆到两个块，汇总出来的数字对不上。改成按「日报」这个天然边界切（一份日报就是一个 map 单元），问题消失。坑二：map 阶段的 max_tokens 设太小（我一开始给 150），摘要被硬截断，后半句的结论丢了，提到 300 后虽然浪费一点但信息完整。坑三：reduce prompt 里没写「保留数字」，模型把「良率 92.3%」改成了「良率较高」——摘要里所有精确数字都被模糊化。后来我在 prompt 里加了一条硬规则：出现的数字原样保留，不改写、不省略。

结论

没有最好的摘要策略，只有匹配文档结构的策略。map-reduce 胜在快，refine 胜在连贯，层级归约胜在你把业务结构注进了切分方式。对我这个场景——文档本来就按人、按天、按周组织——顺着这个结构做层级归约，既拿到接近 refine 的连贯性，又保住 map-reduce 的速度。现在我的默认选择是：先看文档有没有天然的层级，有就用层级归约；没有再退回 map-reduce；refine 只留给那些必须逐字精读的极短文档集。
